## vite, importmap

importmapは、バニラJSで、JSモジュールを使いたいときにあったほうがいい機能だけど、viteに比べると、管理はかなり厄介になる。

## javascript, typescript

javascriptは、IDEで無理が出やすい。

特殊な状況以外では、typescriptが無難。

## vue, react

reactはメンテナンスコストが高くなりがちなので非推奨。

このレポジトリ内にあるコードは、あくまで、実装例です。

なぜ、非推奨なのかは、実装例でVueと比較してあるので、見ればわかると思う。

reactは、革新的なアイデアだったけど、テンプレートエンジンではないため、しんどくなる部分がある。

vueは、reactからしんどい部分を除去してあるので、比較的、実用的。

全体を比較すると、よくわかると思うけど、そこまで全体を見ることは、一般的には難しいと思う。

よくわからない人は、vue、composition API、defineModelでいいと思う。

reactは、構造上、実装のための実装がかさんでいくようにできている。

コボルのような達成感は得られるだろうけど、メンテナンスが大変になっていく。

## アトミックデザイン

アトミックデザインはあくまで実装例で非推奨。

理由は、依存が複雑になって変更が危険になるためです。

個人的な趣味の範囲で実装すること自体は楽しいと思います。

ただし、個人的な趣味の範囲にとどめて、実務では利用しないほうが無難。

## Turbo Drive

なぜ非推奨かは、実装例を見ればわかると思う。

これを使うとMPAとSPAの要素がまざった実装になり複雑化する。

予期せぬ副作用が起きやすい。

さらに、今の技術だと、使っても使わなくても、UXにほとんど違いがない。

## お手軽SPA風ツール

## ユニットテスト

ユニットテストの特徴はこんな感じ。

- テストは腐りやすい。
- モックだらけ、仕様をなぞるだけのテストは負債になりやすい。
- メンテ不能なテストも負債。
- 人が間違いやすい箇所に絞り込んだほうが効率的。
- 関数、サービスクラスをテストして、コントローラーなどでは頑張らないほうがいい。

テストを作ることは、その後のメンテナンスを延々とし続けなくてはいけなくなるので、負債を増やすことと同じ。

負債とメリットのバランスをとることが、WEBアプリケーションでは重要だと思う。

### ただし、網羅的なテストが必要な場合もある

フレームワークとかを作り、安定した状態で提供し続けなくてはいけない場合は、網羅的なテストは必須になる。

ただし、WEBアプリケーションで同じことをすると、難しい状態に陥ることもある。

これも、フレームワークを作る人の話を、WEBアプリケーションを作る人が、鵜呑みにしてはいけない理由の一つ。

## イノベーション

イノベーションは、新しいことをすることと誤解されがちだけど、潜在的ニーズを満たした結果、そう評価されること。

つまり、「イノベーション」自体は、あくまで大衆的な評価のため、目標にはできない。

目標にできるのは「潜在的ニーズを満たすこと」。

そのため、イノベーションという単語を多用していると、「潜在的ニーズを満たすこと」をしないで、「新しいこと」を広めることだけをするようになっていく。

新しい技術には、そのようなものもあるので、見極めが必要。

言葉だけが、独り歩きすることがある。

### 似た状態のこと

承認欲求は、人の役に立つことをして、称賛されたり、対価として報酬を受け取ると満たされる。

あくまで、他人との関係性によってのみ得られる。

自己肯定感という単語も、イノベーションと同じように、独り歩きしている言葉だと思う。

自己肯定感は、承認欲求を満たすプロセスの結果得られるものだけど、自己肯定感を多用する人は、そのプロセスを無視して、自己肯定感だけを得るような考えを広めるようになる。

ただ、承認欲求が満たされることは、イノベーションと違い、比較的簡単に実現できるという違いはある。

適性に合ったことをすると、比較的楽に、他の人にとって価値ある結果が出やすいので、楽に、承認欲求も満たされることになる。

ただし、適性が活かされない環境では効果がないという現実もあるため、そのような状態に置かれてしまった人は、承認欲求が満たされなくなり、上記のようになりやすい。

さらに、適性が合わないことについては、感覚的にわからないため、形式だけを求めるようになる。

それによって、悪循環がさらに加速するというのが、よくあるパターンだと思う。

## コメント

railsなどでは、コメントをしない文化があるけど、railsの製作者が言っていたのは、コメントがなくてもわかるようなコードを書こう、ということであって、コメントをしないでいい、ということではない。

フレームワークを作る人が言っていることを、アプリケーションを作る人が、正しく解釈しないで、言葉尻だけとらえて、コメントがないアプリケーションを作ると、メンテ不能のシステムが出来上がる。

### if文の内部のコメント

空気を読まないでいいので、これが一番、不具合が起こりにくく、認知負荷が低い。

```
if (条件) {
  // 〇〇の時

  // 〇〇をする
  処理()
}
```

これ以外だと、空気を読む必要が出てきて、誤解が生じやすい。

### コメントの頻度

コメントは、役に立つけど目立たないくらいが、一番、認知負荷を下げられると思う。

同じくらいいいのは、役に立つコメントが、みっちり書かれている状態。

あまりよくないのは、目立つけど役に立たないコメント。

一番、メンテナンスコストが高いのは、コメントゼロ状態。

### 腐ったコメント

コメントが嫌われる理由の一つに、腐ったコメントがある。

コメントは「この先崖」という注意看板に近いので、腐ったコメントでも、消すより、直すほうが無難。

腐りやすいコメントのトップクラスのものは、パラメーターや、返り値のコメントだと思う。

この手のコメントは、必要最小限にとどめて、義務にしないのも、コメントを腐らせないためのコツだと思う。
